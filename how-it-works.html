How p5.strandsReveal works

A short tour of what the addon actually does, and why this approach was chosen over the more obvious ones.

What we're trying to see

When you write a p5.strands shader callback like:

function invertFilter() {
  filterColor.begin();
  let c = getTexture(filterColor.canvasContent, filterColor.texCoord);
  filterColor.set([1 - c.r, 1 - c.g, 1 - c.b, c.a]);
  filterColor.end();
}

…and pass it to buildFilterShader(invertFilter), p5.strands doesn't run that function directly. It first transpiles the source: arithmetic operators become add/mult/etc. calls on strands nodes, member assignments are rewritten, control flow is restructured, and so on. The resulting JavaScript is what actually executes to build the IR that the GLSL/WGSL backends compile.

You can already get the generated GLSL out of strands. The transpiled JavaScript, however, only exists as a string inside the transpiler — it gets handed straight to new Function(...) and discarded.

Where the transpile happens

All the buildXxxShader functions (buildFilterShader, buildMaterialShader, buildColorShader, buildNormalShader, buildStrokeShader) are one-line wrappers around baseXxxShader().modify(callback). The strands addon installs its transpilation logic by overriding p5.Shader.prototype.modify. So the single right place to intercept is modify — one wrap covers every build*Shader entry point.

Inside that overridden modify, the relevant call looks like this (paraphrased from src/strands/strands_transpiler.js): 

const transpiledSource = escodegen.generate(ast); // the JS we want
// ...regex-extract params and body from transpiledSource...
const internalStrandsCallback = new Function(
  '__p5',
  ...paramNames,
  body,
);
return () => internalStrandsCallback(p5, ...paramVals);

The string is right there for a moment, then it's lost.

The approach used: shim Function across one call

The transpiler eventually constructs the runtime callback with new Function('__p5', ...paramNames, body). Function is a global, so substitute the global for the duration of one modify() call, capture the arguments, then restore it. 

const origModify = p5.Shader.prototype.modify;

p5.Shader.prototype.modify = function (cb, scope, options) {
  if (typeof cb !== 'function' && typeof cb !== 'string') {
    return origModify.call(this, cb, scope, options);
  }

  const RealFunction = globalThis.Function;
  let captured = null;

  function ShimFunction(...args) {
    if (args.length >= 2 && args[0] === '__p5' && !captured) {
      captured = { params: args.slice(0, -1), body: args[args.length - 1] };
    }
    return new RealFunction(...args);
  }
  ShimFunction.prototype = RealFunction.prototype;

  globalThis.Function = ShimFunction;
  let shader;
  try {
    shader = origModify.call(this, cb, scope, options);
  } finally {
    globalThis.Function = RealFunction;
  }

  if (captured) {
    shader._strandsTranspiledJS = {
      original: typeof cb === 'string' ? cb : cb.toString(),
      params: captured.params,
      body: captured.body,
      formatted: `function (${captured.params.join(', ')}) {\n${captured.body}\n}`,
      timestamp: Date.now(),
    };
  }
  return shader;
};

Why this is safer than it looks

  • The shim window is one synchronous call. modify doesn't await anything; the finally always restores Function before any other code can observe the swap.
  • It only captures calls whose first arg is '__p5'. That's the strands transpiler's signature. If something else happens to call new Function(...) during modify, it's passed through to the real Function and not recorded.
  • No reliance on transpiler internals. If strands tweaks its AST passes or its escodegen options, this addon keeps working as long as the final step still goes through new Function(...) with __p5 as the first arg.

Order of registration

p5.registerAddon runs synchronously (src/core/main.js). p5 v2 registers the strands addon itself when the bundle loads, so by the time p5.strandsReveal.js runs, p5.Shader.prototype.modify is already the strands-wrapped one. The script order in index.html reflects that: 

<script src="https://cdn.jsdelivr.net/npm/p5@2.2.3/lib/p5.js"></script>
<script src="./p5.strandsReveal.js"></script>
<script src="./sketch.js"></script>

Reading the captures back

Several equivalent ways, pick whichever fits:

  • myShader._strandsTranspiledJS — record attached directly to the shader.
  • getStrandsTranspile(myShader) — helper, returns the record.
  • revealStrandsTranspile(myShader) — helper, pretty-prints original and transpiled to the console.
  • p5.strandsReveal.last — the most recent capture across any shader.
  • p5.strandsReveal.history — an array of every capture this session.
  • p5.strandsReveal.log() / .clear() — namespace methods.
Caveat. If a future build of p5 inlines or aliases Function at module load (some bundlers do this for built-ins), the global swap won't be seen by the transpiler. That hasn't happened in the versions tested, but it's the failure mode to keep an eye on.

Alternative approaches I considered, and why I didn't pick them

  • Proxy buildFilterShader and friends. Wrong layer. There are five+ such functions, and they all funnel into modify. Wrap the funnel, not each tributary.
  • Re-import transpileStrandsToJS and call it myself. It's exported, but it doesn't return the source string — only the wrapped callable. Reproducing the regex extract means depending on transpiler internals.
  • Re-run the transform from scratch with my own copy of acorn + escodegen. Possible but heavy: the transpiler does several AST passes specific to strands. A separate copy will drift from the real one over p5 versions.
  • Patch escodegen.generate. Cleanly captures the exact string, but escodegen is bundled inside p5 — I can't reach the module instance the transpiler closed over.

Definitely not exposed?

I checked the strands source carefully to check the API doesn't have a more direct way to access the transpiled code. As of p5 v2.2.3 the codebase actively confirms it:

  • src/strands/p5.strands.js:136 has the comment “TODO: expose this, is internal for debugging for now” sitting directly above the lines that force options.parser = true and options.srcLocations = false. The maintainers note explicitly that the parser knobs are not yet exposed.
  • Those same two lines unconditionally overwrite whatever options the caller passed in — so attempting shader.modify(cb, scope, { parser: false }) from outside is silently ignored.
  • src/strands/strands_transpiler.js only logs transpiledSource, body, or paramNames on error paths (lines 1774, 1800–1801). On the happy path the body string is passed straight into new Function(...) and not retained.
  • transpileStrandsToJS is exported but only imported by p5.strands.js itself, and it returns the wrapped callable, not the source string — so even calling it directly from an addon wouldn’t hand you the JS without re-running the regex extraction.
  • src/strands/strands_api.js exposes user-facing nodes, operators, and helpers, but no debug/inspect surface. There is no environment flag (no DEBUG_STRANDS, no verbose, etc.) anywhere in the strands tree.
  • contributor_docs/p5.strands.md describes the transpile pipeline but doesn’t document any way to read the intermediate JS from a sketch.

So until that TODO ships, the only way to see this code from outside the engine is to set a breakpoint inside the running callback and poke around in the debugger — or do something like this addon.
